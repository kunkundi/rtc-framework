# Jetson H.264 分辨率切换硬件测试报告

> 测试日期：2026-08-21<br>
> 仓库基线：`standalone` 分支，提交 `6c2d6e3b098d` 加本报告对应工作区修改

## 1. 测试结论

优化后有明显且可重复的进步：

- 优化前实现第一次从 1920×1080 切换到 1280×720 后即触发捕获面 `Broken pipe`，编码器进入错误状态，新分辨率首帧在 3 秒超时内没有返回。
- 最终方案在底层完成 300 次双向切换、在 WebRTC `JetsonH264EncoderImpl` 接口完成 180 次双向切换，全部成功。
- 底层 300 次测试的切换操作 p99 为 6.69 ms，首个可独立解码帧回调间隔 p99 为 60.86 ms、最大 63.79 ms。
- WebRTC 封装层 180 次测试的首个可独立解码帧回调间隔 p95 为 63.74 ms、最大 71.24 ms。
- 所有优化后切换首帧均同时包含 SPS 和 IDR，没有把新分辨率的不可独立解码帧交给 WebRTC。
- 两个测试进程并发、合计四个 NVENC 会话时也全部通过；并发负载下底层最大回调间隔为 74.65 ms。

以优化前“3 秒仍无首帧”的超时下界计算，优化后 WebRTC 最大 71.24 ms 至少缩短了 97.6%。优化前实际上已经进入硬件错误状态，因此真正收益不仅是耗时降低，还包括从“切换不可用”变为“可持续双向切换”。

## 3. 测试方法

### 3.1 分辨率序列

每轮执行以下双向阶梯：

```text
1920×1080
  -> 1280×720
  -> 960×540
  -> 640×360
  -> 960×540
  -> 1280×720
  -> 1920×1080
```

编码参数为 H.264 Baseline、30 fps、6 Mbps CBR、无 B 帧、长 GOP。输入使用每帧变化的合成 I420 图案，以避免静态黑帧不能代表动态画面的编码路径。

### 3.2 指标定义

- `reconfigure`：开始分辨率切换到切换 API 返回的时间。
- `callback_gap`：旧分辨率最后一个编码回调到新分辨率首个可交付编码回调的时间。
- `first_frame`：开始提交新分辨率输入到首个可交付编码回调的时间。
- `standby_refresh`：在后台销毁旧会话、创建最高分辨率热备并实际编码一帧完成预热的时间。该时间不进入实时切换临界路径。
- `decodable keyframe`：码流同时包含 H.264 SPS NAL（类型 7）和 IDR NAL（类型 5），并由 WebRTC 标记为关键帧。

底层基准直接调用 `JetsonEncoder`。集成测试通过 `JetsonH264EncoderImpl::InitEncode()`、`SetRates()`、`Encode()` 和 `EncodedImageCallback`，覆盖 WebRTC 封装、后台热备线程和 generation 隔离。

## 4. 优化前基线

当前原实现的 `JetsonEncoder::Reconfigure()` 同时停止输出面、捕获面和捕获 DQ 线程，并释放两侧缓冲区后重新启动。

真实硬件上的第一次 1920×1080 → 1280×720 切换结果：

| 指标 | 结果 |
| --- | ---: |
| `Reconfigure()` 调用 | 15.194 ms |
| 捕获面状态 | `Broken pipe` |
| `encoder_->isInError()` | true |
| 新分辨率首帧 | 3 秒内未返回 |
| 成功切换 | 0/1 |

日志中同时再次出现 `NvMMLiteOpen`/`NvMMLiteBlockCreate`，说明原路径实际上重新打开了 NVENC block。API 本身在约 15 ms 返回并不代表切换完成，编码器随后已经无法继续接收帧。

由于基线在第一次切换即失败，无法得到有统计意义的 p50/p95/p99 分布；将它与优化后的稳定分布直接计算百分比时必须注意这一点。

## 5. 中间方案发现的问题

### 5.1 仅输出面 DRC 的短测结果

按 NVIDIA 官方 `01_video_encode` 样例，只停止并重建输出面后，短测中切换 API 可以降到约 1.4～5.4 ms，首帧回调也恢复到 25 ms 以内，并且不再重新打开 NVENC block。

但 Jetson R36.4.7 在 DRC 后通常先输出“新 SPS + 非 IDR 图像”。如果直接把这帧交给 WebRTC，接收端不能保证从该帧开始可靠解码。最终实现会丢弃它，在下一输入帧前再次请求 IDR。

### 5.2 低到高 DRC 不可长期使用

虽然单轮低到高切换偶尔成功，连续双向压力测试在第 22 次切换后出现：

```text
VENC: NvVideoEncBlockReportError: BlockSide error 0x4
Output Plane: Error while Qing buffer: Invalid argument
```

这与 NVIDIA 官方样例“动态分辨率仅支持高到低”的限制一致。因此最终实现明确拒绝单会话低到高 DRC，不能把一次短测成功当成平台能力。

## 6. 最终实现方案

最终采用高到低 DRC 与热备会话组合：

1. 活跃编码器降低分辨率时，只排空并重建 V4L2 输出面；捕获面、捕获缓冲区和 DQ 线程保持运行。
2. `JetsonEncoder::Reconfigure()` 明确只允许当前分辨率向下切换，拒绝低到高调用。
3. 后台保持一个以最高分辨率创建的热备 NVENC 会话，并真实编码一帧完成固件、缓冲区和 DQ 路径预热。
4. 升分辨率时，对热备会话执行最高分辨率到目标分辨率的向下 DRC，然后交换活跃会话。
5. 旧会话在后台线程销毁，并创建、预热新的最高分辨率热备；销毁/创建不会阻塞实时编码线程。
6. 如果升档发生时热备尚未准备完成，暂时丢弃输入帧并等待后台完成，不在实时线程同步创建编码器。
7. 每个输入帧使用唯一 V4L2 时间戳关联 `CaptureTask`。DRC 后同一输入产生
   多个 coded buffer 时保留原任务直到目标 SPS+IDR 到达，不再按 FIFO
   错误消费下一帧任务或提前回收下一帧 output buffer。
8. 码率和帧率均通过 Jetson API 原地更新，无须重建会话。
9. `Release()` 采用 500 ms 有界宽限期保留会话，并用在途回调屏障保证
   返回后不会再调用已注销的 WebRTC callback。

普通切换最多维持两个 NVENC 会话：一个活跃、一个最高分辨率热备。测试中后台热备补充平均约 50 ms，而网络自适应的升档迟滞通常应为数秒，因此有足够时间在下一次升档前恢复热备。

## 10. 限制与后续验证

- 本次测试使用动态合成 I420 图案，能隔离编码器切换耗时，但不是完整摄像头到远端显示的玻璃到玻璃时延。
- 已增加[Orin 弱网控制工具与测试指南](jetson_weak_network_test.md)，并启用 QualityScaler、QP 阈值和实际分辨率码率阶梯。当前内核缺少 `netem/IFB`，所以主机可直接使用的后端是 `iptables` 限速 policing 和随机丢包；完整双端自动升降档录像仍需在确认媒体对端地址后执行。
- NVIDIA Multimedia API 公共类在主动销毁会话、`STREAMOFF` 捕获面时会打印 `Broken pipe`。它出现在后台回收或进程退出阶段，测试进程退出码仍为 0，与运行中发生的 block error 不同。
- 热备会增加一个 NVENC 会话及其缓冲区、功耗和内存占用。当前 Orin 上四会话通过，但正式多摄像头部署仍应监控温度、频率、功耗和编码 p99。
- 本次仅验证 L4T R36.4.7。R35、其他 R36 小版本和不同 Jetson SKU 必须复测。
- 默认码率阶梯、QP 阈值和 WebRTC 质量缩放已经落地；播放抖动缓冲、真实道路素材标定和多种网络制式下的迟滞参数仍需端到端调优。

### 10.1 QualityScaler 启用后的硬件回归

| 测试 | 切换数 | 平均回调间隔 | p95 | 最大 | 有效 SPS+IDR |
| --- | ---: | ---: | ---: | ---: | ---: |
| 底层混合切换 | 300 | 46.195 ms | 57.814 ms | 61.413 ms | 300/300 |
| WebRTC 封装层 | 180 | 52.360 ms | 65.227 ms | 68.399 ms | 180/180 |

底层切换 API 平均 2.841 ms、p95 5.302 ms、最大 8.280 ms。开启 QualityScaler 和真实码率阶梯后，原有 DRC/热备切换性能与首帧可解码性没有退化。

### 10.2 WebRTC 重复 InitEncode 复用验证

真实 WebRTC 分辨率适配会再次调用 `InitEncode()`。封装层已经改为保留原始最高会话分辨率：降分辨率直接复用当前编码器执行输出面 DRC，升分辨率优先交换预热编码器，不再在每次 `InitEncode()` 中无条件销毁主编码器和热备。

集成测试已经改为每次分辨率切换前都调用 `InitEncode()`。Orin 硬件十轮共 60 次切换全部成功，60/60 首帧包含有效 SPS+IDR；复用初始化平均 3.151 ms、p95 7.237 ms、最大 8.447 ms。平均回调间隔为 52.366 ms，p95 65.386 ms；测试与正在运行的五路 `rtc_edge` 并发时出现一次 95.374 ms 最大值。另从 640×360 会话首次扩展到 960×540 时，`InitEncode()` 在 0.155 ms 内返回，目标热备在后台创建，首帧回调间隔 45.967 ms，旧编码器不会在调用线程同步销毁。

编码器同时增加每秒 QP 窗口日志：

```text
[JetsonEnc][qp] encoder=... size=1920x1080 avg=22.83 min=16 max=29 samples=24 missing=0 bitrate=6000000 fps=30 thresholds=32/36
```

动态合成图案在 1920×1080、6 Mbps 下得到的两个连续窗口平均 QP 分别为 22.56 和 16.81，证明 QP 解析和聚合链路有效。默认缩放阈值设为 32/36；真实道路正常网络验证见下一节，弱网侧仍需继续复核高阈值。

### 10.3 真实道路摄像头 QP 初始标定

2026-08-21 使用 `rtc_edge`、真实双目摄像头和实际对端连接进行约 40 秒采样。主视频流稳定在 `960x540@30fps`，目标码率约 `2.05 Mbps`，共取得 39 个一秒 QP 窗口：

- 窗口平均 QP 的总体均值：`21.85`
- 最低窗口平均 QP：`21.63`
- 最高窗口平均 QP：`24.37`
- QP 解析缺失：`0`

正常网络下的道路画面 QP 明显低于上调阈值 32，因此将缩放阈值设为 `32/36` 能保留足够的上调余量，同时避免原有宽死区。高阈值 36 仍需在限速、丢包阶段继续验证；本次自动弱网注入因运行终端的 `sudo` 需要交互密码而未执行，未留下任何网络规则。

### 10.4 双目主流 720p 升档门槛

现场双目输入和拼接输出均支持 `1280x720`。旧进程启动时曾创建 1280×720 编码器，但现场初始分配码率约 `1.646 Mbps`，低于原 720p 的 `1.7 Mbps` 保持下限，因而很快降到 960×540；后续 `2.8 Mbps` 升档门槛又阻止它恢复。540p 道路流在约 `1.0～1.65 Mbps` 下的平均 QP 约为 23，仍有较大清晰度余量。

720p 阶梯调整为：`1.6 Mbps` 推荐启动、`1.2 Mbps` 保持下限、`4.5 Mbps` 上限。链路达到约 1.6 Mbps 时允许尝试升到 720p；跌破约 1.2 Mbps 或 QP 持续超过 36 时仍可回退到 540p，避免弱网下强制维持 720p。Jetson 集成测试已覆盖 960×540 → 1280×720 切换和可独立解码关键帧；完整端到端升档需要当前占用摄像头的旧 `rtc_edge` 进程正常重启并加载新动态库后复核。

重启后的现场日志确认双目主流从 960×540 升到了 1440×810，码率约 6.34 Mbps、平均 QP 21.94，已经超过 720 高度。随后 WebRTC 继续清除分辨率限制并直接送入更大的帧，但这一阶段没有再次调用 `InitEncode()`；旧实现没有从 `Encode()` 路径扩大 `session_width_`/`session_height_`，后台线程会反复预热旧尺寸，较大帧一直处于 pending，表现为主流只短暂升档后停止输出。

`Encode()` 现已在发现输入帧超过会话上限时原子更新会话尺寸和 epoch、淘汰不兼容热备，并请求后台创建新尺寸热备。Orin 回归在不再次调用 `InitEncode()` 的条件下完成 960×540 → 1440×810 → 1920×1080 连续扩容，两个升档首帧均包含 SPS/IDR；到达 1920×1080 后继续编码 40 帧无停滞。

### 10.5 摄像头原生 1920×1200 输出验证

双目摄像头每路实际协商为 `1920×1200 YUYV`，每路横向二分之一抽样后拼接输出为 `1920×1200`。原配置在进入 WebRTC 前把 `merged_image` 强制缩放为 `1920×1080`，因此即使摄像头和拼接模块已经提供原始高度，编码流也不可能恢复到 1200。

现已把双目主流上限调整为 `1920×1200`，并增加对应的 30 fps 码率档：推荐启动 `7.0 Mbps`、保持下限 `4.2 Mbps`、最大 `12 Mbps`。H.264 编码能力同时优先声明 Baseline/Constrained Baseline Level 5.1；Orin NVENC 在真实硬件测试中也实际选择了 Baseline Level 5.1，避免使用 Level 4.x 描述超出其 MaxFS 的 1920×1200 码流。

2026-08-21 在 Orin 上将完整切换序列改为 `1920×1200 → 1280×800 → 960×600 → 640×400 → 960×600 → 1280×800 → 1920×1200`，运行三轮得到：

- 18/18 次分辨率切换首帧均包含 SPS、IDR，且可独立解码；
- 输出面重配平均 `2.495 ms`，最大 `7.151 ms`；
- 新分辨率首帧平均 `43.628 ms`，最大 `51.195 ms`；
- 编码回调间隔平均 `46.379 ms`，最大 `58.639 ms`；
- 最高档后台热备刷新平均 `47.366 ms`，最大 `50.896 ms`。

封装层集成测试也完成三轮 18 次切换，并在不再次调用 `InitEncode()` 的条件下完成 `960×600 → 1440×900 → 1920×1200` 连续扩容；到达原生分辨率后持续编码 40 帧无停滞。正式端到端验证需要重启当前仍在运行的旧 `rtc_edge` 进程，使其重新加载新动态库和 `merged_image=[1920,1200]` 配置。

现场重启后主画面仍稳定在 `960×600`。日志表明原生输入、Level 5.1 和新动态库均已生效，但四路未选中的环视轨道虽然只有 1 fps，每路仍被分配约 `1.0～1.9 Mbps`；主流只能在约 `1.2～4.5 Mbps` 间波动。同时原码率表缺少 16:10 中间档，使 `960×600` 的下一次升档接近直接使用 1080p 门槛。

因此增加 `960×600 → 1280×800 → 1440×900 → 1920×1200` 独立码率阶梯，并把 `VeryLow` 辅助轨道的发送上限限制为每路 300 kbps。主画面保持 High 优先级和 12 Mbps 上限；在当前约 4.5 Mbps 的高带宽窗口应先恢复到 `1440×900`，可用码率稳定达到约 7 Mbps 后再升到原生 `1920×1200`。

### 10.6 主画面升到原生分辨率后冻结的修复

现场运行时主流先以 `1440×900@30fps` 编码，约 3 秒后低 QP 触发 QualityScaler 升到原始 `1920×1200`，但升档后编码器没有再收到输入帧。最终确认根因不在 NVENC：缩放后的 `VideoFrame` 没有保留 `ntp_time_ms`，WebRTC 会为其合成绝对墙钟 NTP；未缩放原帧却把单调时钟毫秒值填入 NTP 字段。分辨率升档使 NTP 时基突然回退，后续主流帧全部被 WebRTC 当作旧帧丢弃，因此表现为永久停在最后一帧。

修复包括：

- 外部视频源统一使用 WebRTC 实时时钟生成绝对 NTP；
- 视频适配器缩放帧时完整传递输入帧的 NTP；
- 输入输出缓冲改为显式空闲队列，避免 WebRTC 编码队列执行阻塞式 V4L2 DQ；
- DRC 后遇到同一输入产生的额外捕获块时只重排捕获缓冲，不重复阻塞回收输出缓冲；
- 仅为主 16:10 视频流保留热备，四路低优先级辅助流维持单会话，稳定状态共占用 6 个 NVENC 设备句柄。

修复后在真实摄像头和实际 P2P 对端连接下，主流约 4 秒时从 `1440×900` 正常升到 `1920×1200`，随后持续超过 1 分钟以约 30 fps 输出，每秒 QP 窗口均有 30～31 个样本，平均 QP 约 27，未再出现旧 NTP、输出缓冲或编码回调错误。

最终 Orin 硬件集成测试运行 10 轮、共 60 次分辨率切换，结果为 60/60 首帧包含有效 SPS+IDR，平均回调间隔 `55.427 ms`、p95 `67.873 ms`、最大 `101.901 ms`。与修复前一版的平均 `55.588 ms`、p95 `70.367 ms` 相比，平均值基本持平、p95 略有改善；本次修复的主要收益是消除升档后的永久冻结和 DRC 边界死锁，而不是追求平均切换耗时的大幅下降。

### 10.7 弱网频繁切换冻结的最终修复与复验

后续真实弱网联调暴露出两个更深层的状态机问题：

1. Jetson 在一次 DRC 输入后可能先输出 SPS/非 IDR，再输出目标 IDR。旧代码
   把 coded buffer 与输入任务按 1:1 FIFO 关联，额外 buffer 会偷走下一帧
   `CaptureTask`，导致码流、时间戳和 output buffer 回收整体错位。
2. output plane 已经 `STREAMOFF/deinit` 后，如果重新设置格式、申请缓冲或
   `STREAMON` 失败，旧代码只返回失败但仍可能把该会话视为健康并再次复用。

最终修复为每个 QBUF 设置 `V4L2_BUF_FLAG_TIMESTAMP_COPY` 和唯一时间戳，
capture DQ 按时间戳查找并保留对应任务；无匹配的额外块只重排 capture
buffer，不再消费其他任务。破坏性重配开始后的任一失败都会立即将会话
标记为 unhealthy/abort，由封装层异步退休并创建精确尺寸替代会话。I420
写入还会校验可见尺寸、stride、Jetson 对齐尺寸和 plane allocation，防止
`720×450 -> 720×464`、`360×198 -> 368×208` 的越界读写。

延迟 `Release()` 同时增加 callback in-flight 屏障。聚焦回归测试会故意把
`OnEncodedImage()` 阻塞 50 ms，并从另一线程调用 `Release()`；实测
`Release()` 在回调解除阻塞前不会返回，排除了上层销毁 callback 后的 UAF
窗口。

2026-08-21 最终代码在 Orin 上的复验结果：

| 测试 | 结果 |
| --- | --- |
| WebRTC 集成切换 3 轮 | 18/18 首帧均含 SPS+IDR；平均回调间隔 23.759 ms，p95 38.856 ms，最大 62.868 ms |
| 底层切换基准 10 轮 | 60/60 首帧均含 SPS+IDR；重配平均 3.042 ms、p95 5.553 ms；回调间隔平均 18.622 ms、p95 30.989 ms、最大 32.739 ms |
| `rtc_edge` 真实双目长跑 | 约 98 秒，退出前 `captured=3227`、`sent=3202`，P2P 全程连接 |
| 真实动态升降档 | 启动恢复到 1920×1200；运行中完成 1920×1200 → 1440×900 → 1920×1200，保持 29～30 fps |

真实 `rtc_edge` 日志中共有 76 个 `1920×1200` 的一秒 QP 窗口，全部
`missing=0`；未出现 Surface 分辨率不足、`NvVideoEnc BlockError`、输入或
Plane 尺寸不匹配、`capture-dq:null-buffer` 或不可用会话。运行中一次
1920×1200 → 1440×900 的 output-plane DRC 耗时 5.087 ms，约 10 秒后正常
恢复原生分辨率，证明频繁动态分辨率变化不再导致编码停产。

当前媒体路径由 `[NetPath]` 确认为 `eth2` 上的 host/UDP 直连，远端为
`10.15.73.245`。自动化终端没有可用的交互式 sudo 凭据，因此没有在主机
接口上执行完整 `cycle`；限速/丢包脚本已在独立网络命名空间中完成真实
iptables 规则、DROP 计数和清理验证。

代码复核随后发现：活跃会话和待退休/热备会话的独立 DQ 线程仍可能同时
到达 WebRTC callback。若其中一个回调内部重入 `Release/Register`，只凭
线程局部标志会跳过另一个仍持有旧 callback 的 lease。最终实现因此串行化
同一 wrapper 的外部 `OnEncodedImage()`，并为 callback 注册生命周期增加
epoch。等待 lease 的旧会话帧若跨越 `Release/Register`，会在读取新 callback
前因 epoch 不一致而丢弃。

新增硬件回归先让 Release 前的旧会话帧排队，再在旧回调内部执行
`Release -> Register -> InitEncode`。日志确认旧 waiter 以
`epoch=53 current=55` 被丢弃；新会话回调在旧回调退出前被阻挡 50 ms，
退出后正常恢复。另一线程调用 `Release()` 的屏障测试也通过。

使用包含该最终修复的正式动态库再次运行 `rtc_edge` 约 86 秒，退出前
`captured=2886`、`sent=2841`，主流稳定在 `1920×1200@29～30fps`。本次
取得 69 个原生分辨率 QP 窗口且全部 `missing=0`，上述 Surface、Block、
Plane、capture task、callback 交付和不可用会话错误计数全部为零。

生命周期前置条件与 WebRTC 当前所有权模型一致：允许在
`OnEncodedImage()` 内同步触发 `Release/InitEncode`，但不得在该调用栈内
直接析构编码器对象；对象销毁应由拥有它的编码队列在回调返回后执行。

## 11. 最终判断

优化方案在当前真实 Jetson Orin 上有效。原实现不是单纯“切换慢”，而是在 R36.4.7 上第一次全面重启编码流水线就可能把编码器置为错误状态。最终的“高到低仅输出面 DRC + 低到高热备切换 + 后台回收预热 + SPS/IDR 门控”同时解决了长卡顿、低到高 DRC 不稳定和新分辨率首帧不可解码三个问题，已经具备进入真实 RTC 网络联调阶段的条件。
